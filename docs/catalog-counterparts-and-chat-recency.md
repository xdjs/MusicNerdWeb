## Catalog counterpart contract

During existing profile discovery, a known Deezer identity can propose Spotify, and a known Spotify identity can propose Deezer. Name search supplies bounded Deezer candidates; it is not proof. Matching requires at least two distinct exact ISRCs, a unique winning Spotify credit identity, and the resolved artist name. Collaborator ties, incomplete Spotify results and a full five-result Deezer candidate window remain ambiguous. Unavailable or malformed provider responses are provider failures, not empty catalogs. No result within this bounded sample does not prove an artist has no counterpart anywhere in the catalog.

Automatic attachments retain unique Wikidata proof and otherwise recheck the exact recording-corroborated pair. The existing scoped/locked writer rechecks mapping conflicts, saved exclusions, review decisions and source/target catalog values before writing. Explicit artist decisions remain separate. The database now schedules a `catalog_match` job after artist inserts and updates. MusicNerdAPI runs it in either direction under exact leases and identity locks, with at most four failed attempts and a seven-day expiry. Completed snapshots do not replay; changing an anchor invalidates a running job and schedules the replacement. Reset preserves catalog jobs. Web creation attaches activity lineage and avoids duplicating the legacy Spotify job when the database already queued a counterpart job. Old in-flight jobs remain supported. No provider calls are added to page reads and no production backfill is included.

Profiles with neither catalog are classified as `identity_anchor_required`, without name-only attachment or provider calls. Adding an anchor schedules verified discovery. Existing malformed IDs stay available for review; the database rejects new malformed or blank canonical IDs. Legacy exclusions can receive fresh recording verification, but successful matches remain `exclusion_review_required` and never overwrite those decisions. The exclusion table does not establish whether an old failure was human-authored. Explicit disconnects prevent search and attachment; a private boolean helper exposes no archive contents.

Web owns the shared database migration history, so migrations 0058/0059 and the creation handoff live here. Matching and chat behavior run in MusicNerdAPI. Apply both reviewed migrations before deploying the dependent API worker and compatible Web handoff. Jobs queued during the rollout wait for the API worker, which also defers to any live legacy match; enqueue existing rows only under a separately reviewed repair manifest. No authentication changes are included.

## Chat contract

The streaming chat already loads own social posts, public answers and stored provider snapshots. `searchSources` now supports chronological retrieval and platform/evidence constraints through the existing shared selectors; `readSource` and search results expose publication/activity/retrieval dates. Latest mode excludes unknown and future dates. Latest-release requests prioritize dated catalog evidence instead of treating a newer social post as a newer release.

The prompt requires reading and citing the newest relevant stored item, preserves the date, and qualifies saved evidence as incomplete live coverage. Empty/stale results cannot prove no newer activity. No additional model call, database query or provider fetch is added to saved-source retrieval. Model compliance still needs a live chat/eval check; deterministic tool tests are not proof of a production model answer or latency.
